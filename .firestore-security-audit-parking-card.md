# Parking Card Firestore Security Review

Scope: `parkingCards`, `parkingCardHistory`, `vehicleLogs`, and `auditLogs`.
Target: `(default)` Firestore Standard database in `asia-southeast3`.

## Access and query findings

- Authentication uses Firebase Auth plus the caller's `users/{uid}` record.
- Parking-card writes are site-scoped. Management writes require Manager/Admin;
  vehicle entry and exit also permit active operational roles.
- Card lookup uses `site_id` plus exact normalized QR/card fields.
- History lookup uses `site_id` plus `parking_card_id`; the corresponding
  composite index is declared in `firestore.indexes.json`.
- `parkingCardHistory` is append-only. Client update and delete are denied.
- History creation validates a strict schema, enum, string bounds, caller UID,
  active site, and server timestamps on both time fields.

## Devil's advocate checks

- Public read/list: denied because an active authenticated user is required.
- Cross-site read/write: denied by `activeSiteId()`.
- History mutation/deletion: denied unconditionally.
- UID spoofing: denied because `operator_id` must equal `request.auth.uid`.
- Type juggling and required-field omission: denied by the domain validator.
- Oversized strings and schema pollution: denied by size checks and `hasOnly`.
- Invalid event type: denied by the immutable event enum.
- Timestamp manipulation: mitigated by requiring Firestore timestamp values;
  application writes use `serverTimestamp()`.
- Query mismatch: history query fields match the declared composite index and
  site-scoped read rule.
- Orphan history: intentionally permitted for `DELETED` history preservation;
  the event remains site- and identity-scoped after the card is deleted.
